# Interaction Rules

## 질문 우선

- 요구사항이 모호하면 구현 전에 먼저 질문.
- 여러 해석이 가능한 경우 선택지를 제시하고 확인받기.
- "알아서 해줘" 라도 핵심 결정 사항은 확인.

## 결정 기록

- 확정 결정의 정본은 **CLAUDE.md 3절**, 미해결 사항은 **PLAN.md 미해결 표**, 도구·버전 결정은 **docs/tooling.md** (이 저장소에 ADR 은 없다).
- 새 아키텍처 결정(기술 선택·패턴 도입·구조 변경)이 내려지면 위 정본 중 맞는 곳에 기록하고, 세션 안에만 남기지 않는다.

## 변경 범위 확인

- 여러 모듈(bcm-api·bcm-bat·domain·infra·support)에 걸치는 변경은 영향 범위를 먼저 파악하고 보고.
- domain·support 등 공통 모듈 변경 시 의존하는 모듈에 미치는 영향 확인.
- DB 스키마 변경이 수반되는 경우 명시적으로 알리기 (03-bcm-db 가 정본 — 어긋나면 설계 대조 먼저).

## 커밋 단위

- 논리적 단위로 나눠서 커밋 (기능 추가·리팩토링·버그 수정을 한 커밋에 섞지 않기). 테스트 수정은 구현과 별도 커밋.
- 커밋 메시지는 **한글 서술형 현행 유지** (예: "T0.1 Gradle 멀티모듈 골격 — …"). conventional commits 형식은 쓰지 않는다.
- 마일스톤 단위 커밋·Co-Authored-By 트레일러는 CLAUDE.md 6절이 정본.

## Git Worktree 활용

- 현재 작업 중인 브랜치와 다른 기능을 병렬로 작업해야 할 때 worktree 로 격리.
- 다른 브랜치 코드 리뷰/확인 시 현재 작업을 stash 하지 말고 worktree 로 전환.
- worktree 생성 전 현재 작업 상태(브랜치·변경사항)를 사용자에게 알리고 확인받기.
- 작업 완료 후 worktree 정리 여부를 사용자에게 확인.

## 코드 변경 시

- 기존 코드를 먼저 읽고 프로젝트 컨벤션을 파악한 후 수정.
- 요청받지 않은 리팩토링·개선·주석 추가 금지.
- 삭제하는 코드가 다른 곳에서 참조되는지 확인.

## 불확실할 때

- 확신 없는 기술적 사실은 추측이라고 명시 (벤더 동작은 CLAUDE.md 0절 — 추측 금지, 96·97·QnA 근거만).
- 두 가지 이상 접근 방식이 있으면 장단점과 함께 제시하고 선택 요청.
- 프로젝트 컨벤션과 일반적 best practice 가 충돌하면 프로젝트 컨벤션 우선.
