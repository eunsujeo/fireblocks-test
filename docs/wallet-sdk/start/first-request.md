---
title: 첫 요청
description: 계정을 만들고 입금 주소를 받기까지
---

_읽는 사람: 파트너사 개발자. Wallet API를 처음 부르는 데 필요한 순서만 다룹니다._

계정 하나를 만들고 그 계정의 입금 주소를 받는 데까지가 이 페이지입니다. 여기까지 오면 나머지는
자금이 움직이는 이야기입니다.

**여섯 단계이고 그중 셋만 파트너사가 부릅니다.** 앞의 셋은 준비이고, 마지막 하나는 부르는 것이
아니라 기다리는 것입니다.

## 1. API 키는 받아서 시작합니다

**파트너사가 첫 요청 전에 만드는 것은 없습니다.** 워크스페이스·테넌트·vault 순서로 먼저
만들어지고, 파트너사는 그 끝에서 나온 API 키 원문 하나를 받습니다.

워크스페이스는 Wallet SDK를 도입한 회사 하나이고 최상위 격리 컨테이너입니다. 테넌트는 Workspace
아래에서 Account를 묶는 계정 체계 하나이고, 파트너 대상 API의 격리
키입니다([계정 계층](/accounts-wallets/accounts)). vault는 Wallet의
그룹입니다([지갑 계층](/accounts-wallets/wallets)).

- **플랫폼이 등록합니다**: 워크스페이스와 네트워크. 워크스페이스는 플랫폼이 밖에서 등록하고,
  네트워크도 플랫폼 수준에서 관리합니다.
- **워크스페이스 운영자가 등록합니다**: 테넌트·API 키·토큰·워크스페이스 vault.
  운영자 표면([Admin API](/reference/admin))으로 등록해야 쓸 수 있습니다.
- **파트너사가 받습니다**: 등록된 테넌트의 API 키 원문.

순서는 워크스페이스 개통 → 테넌트 등록 → 그 테넌트의 API 키 발급입니다. 자세한 흐름은
[온보딩](/accounts-wallets/onboarding)에 있습니다.

### 지금은 이 경로가 셀프서비스가 아닙니다

어드민 권한과 정책 자체를 바꾸는 연산인 어드민 액션([자세히](/policy/rule/reference)) 카탈로그에
온보딩 다섯 액션이 아직 등재돼 있지 않습니다. **그 경로로 보낸 판단 요청은 받지 않고, 그때까지
온보딩은 플랫폼이 대행합니다.** 판단 요청은 한 업무 요청을 두고 엔진이 소유하는 판단
기록입니다([자세히](/policy/signing-gate)).

**대행 절차는 아직 이 사이트에 없습니다.** 누구에게 무엇을 요청하고 무엇을 돌려받는지가 문서로
남아 있지 않습니다. 그때까지 키가 필요한 파트너사는 도입을 담당한 플랫폼 쪽에 직접 문의합니다.
진행 상황은 [변경 이력](/changelog)에서 추적합니다.

### 키 원문은 한 번만 볼 수 있습니다

발급은 승인 게이팅을 거치므로 생성 응답에 원문이 들어가지 않습니다. 승인 게이팅은 어드민 액션이
승인자의 확인을 거쳐야 실행되는 통제입니다([자세히](/policy/sequences/approval-gate)).

승인이 끝난 뒤 원문 조회 오퍼레이션이 한 번 내주고, 그 조회로 값이 소멸합니다.

**두 번째 조회는 실패합니다.** 보관 시한이 지나도 같습니다. 그 뒤에 원문을 얻는 길은 재발급뿐이라,
파트너사는 받는 즉시 시크릿 매니저에 넣습니다.

## 2. 부르는 표면은 Wallet API 하나입니다

표면은 계약 소유자와 인증 방식이 하나로 정해지는 API 경로 묶음입니다. 표면이 다섯이지만
파트너사가 부르는 것은 [Wallet API](/reference/wallet) 하나입니다. 경로는 전부 `/api/v1/`로
시작합니다.
다섯이 무엇이고 누가 부르는지는 [표면과 인증](/start/authentication)에 있습니다.

**호스트는 이 사이트에 없습니다.** 환경마다 다르고 아직 확정 서술이 없어, 키를 받을 때 함께
확인합니다. 아래 경로는 그 호스트 뒤에 붙는 부분입니다.

## 3. 인증은 API 키 헤더 한 줄입니다

받은 API 키 원문을 `X-API-KEY` 헤더에 넣습니다.

```
X-API-KEY: <API 키 원문>
```

**스코프를 함께 보내지 않습니다.** `workspaceId`도 `tenantId`도 요청에 싣지 않습니다. 그 키가
어느 테넌트인지를 서버가 알고 있습니다. 왜 그런지는 [표면과 인증](/start/authentication)에 있습니다.

## 4. 계정을 만듭니다

최종 사용자 한 명이 계정 하나입니다. 파트너사가 발급한 사용자 식별자인
`referenceId`([자세히](/accounts-wallets/accounts))를 함께 보냅니다.

```
POST /api/v1/accounts
```

```json
{ "referenceId": "user-8f21c0" }
```

**개인정보는 이 값에 넣지 않습니다.** 파트너사 내부 식별자만 담는다는 것이 연동 계약이고, 그 계약이
이 값을 평문으로 저장하는 근거입니다.

응답 201이 계정 식별자(`acc-`로 시작)를 돌려줍니다. 이 호출은 승인을 거치지 않고 요청 안에서
끝납니다. 계정 생성은 자금을 움직이지 않기 때문입니다.

### 이미 있는 `referenceId`면 400입니다

`referenceId`는 같은 테넌트 안에서 유일합니다. 이미 쓴 값으로 만들면 거부되고, 그때는 조회로
기존 계정을 찾습니다.

```
GET /api/v1/accounts?referenceId=user-8f21c0
```

재시도 경로에서 이 조회가 필요합니다. 생성 응답을 놓쳤을 때 같은 계정에 도달하는 유일한 길입니다.

## 5. 계정 지갑을 만들고 주소를 받습니다

지갑은 토큰 하나를 담습니다. 토큰은 Network 위의 자산이고 Wallet이 담는
단위입니다([카탈로그](/accounts-wallets/catalog)). 그래서 만들기 전에 어느 토큰인지를 정해야 합니다.

```
GET /api/v1/tokens
```

이 목록에는 토큰과 소속 네트워크가 모두 활성인 것만 나옵니다. 파트너 계약에 상태 필드가 없어,
목록에 있다는 사실 자체가 "쓸 수 있다"는 신호입니다.

거기서 고른 `tokenId`로 지갑을 만듭니다.

```
POST /api/v1/accounts/{accountId}/account-wallets
Idempotency-Key: <파트너사가 만든 값>
```

```json
{ "tokenId": "tok-1234567890abcdef" }
```

응답 201이 `walletAddress`를 돌려줍니다. **이 주소를 최종 사용자에게 건네면 준비가 끝납니다.**

### 미리 알아 둘 것이 둘 있습니다

**`Idempotency-Key`는 필수 헤더인데 아직 동작하지 않습니다.** 값을 보내야 요청이 통과하지만 서버가
받아서 버립니다. 그래서 재시도 중복을 막지 못하고, 응답을 놓친 파트너사는 목록 조회로 확인합니다.

```
GET /api/v1/accounts/{accountId}/account-wallets
```

주소를 재발급해도 계정과의 연결은 끊기지 않습니다. 발급 단위는 주소가 아니라 지갑이고 주소는
거기 붙는 값이라, 보안 사고나 지갑 분실 상황에서 서비스가 계속 동작합니다.

## 6. 입금은 부르지 않고 기다립니다

**입금 API는 없습니다.** 그 주소로 온체인 전송이 들어오면 시스템이 관측해 입금 기록을 만듭니다.
파트너사가 부를 것이 없습니다.

들어온 자금은 확정되면 동결 상태가 됩니다. 동결은 입금을 확정 시 fail-closed로 잡아 두는
상태입니다([자금 동결](/fund-flows/release)). 온체인 입금은 거부할 수 없어서 모든 입금이 같은 경로를
거치고, 그것을 푸는 것은 명시적인 해제 요청입니다.

조회는 계정 단위입니다.

```
GET /api/v1/accounts/{accountId}/deposits
```

여기서부터는 [입금](/fund-flows/deposit)이 이어받습니다.
