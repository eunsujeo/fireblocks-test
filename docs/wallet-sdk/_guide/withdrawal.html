출금과 오입금 반환

출금 유형에 따라 출발 지갑, 목적지, 호출 권한과 승인 경로가 달라집니다.

이 페이지 목차
출금 유형수취 주소 등록고객 출금 요청서명과 출금 완료실패와 재조회

출금 유형

유형자금 경로대상·통제
고객 출금WorkspaceVault → 외부 주소Account에 귀속되는 고객 출금. 파트너 API
자체 출금WorkspaceVault → 회사 외부 주소회사 자산의 이동. Workspace 범위의 운영 경로
오입금 반환AccountWallet → 해당 입금의 원래 송신 주소운영자 경로. 문서는 승인과 서명 통제를 요구하며 임의 목적지는 허용하지 않음

고객 귀속 정보

고객 출금의 출발지는 WorkspaceVault입니다. 출발 Vault와 accountId를 함께 저장하고, 해당 고객의 원장 차감은 파트너가 처리합니다.

참고: 출금 (Withdrawal) ↗

반환 승인 지원 여부

계정 지갑 반환은 운영자 승인·정족수를 요구하는 설계지만 현재 Wallet Admin Approvals API는 고정 응답이며 quorum은 null입니다. 실제 승인 절차 지원을 확인해야 합니다.

참고: 정책 결과와 현재 구현 ↗

수취 주소 등록

수취인 유형문서상 준비현재 제약
NON_CUSTODIAL · 개인 지갑주소록 nonce 발급 → 고객 서명 → 서명 증명으로 주소 등록미등록 주소의 최종 허용·거부는 정책이 결정한다고 설명됨
CUSTODIAL · 외부 VASP수취 주소 확인과 트래블룰 정보 교환을 거치는 설계현재 400 ACCOUNT_WITHDRAWAL_CUSTODIAL_UNSUPPORTED

개인 지갑의 주소 등록은 다음 경로를 사용합니다. nonce 발급과 서명 검증의 상세 필드는 원문 API에서 확인합니다.

POST요청 예시
POST /api/v1/accounts/{accountId}/address-books/nonce
X-API-KEY: <발급받은_API_키>
Content-Type: application/json

{
  "networkId": "<대상_networkId>",
  "address": "<수취_주소>"
}
POST요청 예시
POST /api/v1/accounts/{accountId}/address-books
X-API-KEY: <발급받은_API_키>
Content-Type: application/json

{
  "label": "고객 개인 지갑",
  "networkId": "<대상_networkId>",
  "address": "<수취_주소>",
  "nonce": "<발급받은_nonce>",
  "signature": "<nonce에_대한_고객_서명>"
}

참고: 출금 (Withdrawal) ↗ · 주소록 등록용 지갑 소유 증명 nonce 발급 ↗ · 주소록 등록 (지갑 소유 증명 nonce 서명 포함) ↗

고객 출금 요청

POST요청 예시
POST /api/v1/accounts/{accountId}/withdrawals
X-API-KEY: <발급받은_API_키>
Idempotency-Key: <요청_식별자>
Content-Type: application/json

{
  "sourceVaultId": "<출발_wv_ID>",
  "tokenId": "<출금_tokenId>",
  "amount": "1.25",
  "walletType": "NON_CUSTODIAL",
  "destinationAddress": "<수취_주소>",
  "referenceId": "withdrawal-job-0001"
}

amount는 토큰 표시 단위의 문자열입니다. 예시의 주소와 ID를 실제 값으로 바꿔 요청하고, 201 응답의 withdrawalId를 요청 본문과 함께 저장합니다.

출금 잔액 검증 미구현

고객 출금과 자체 출금에는 선행 잔액 검증이 아직 없습니다. 동결·예약 금액을 제외하지 않고 출금이 진행될 수 있으므로 운영 전에 보완이 필요합니다. 파트너의 잔액 확인만으로는 SDK 내부의 동시 요청까지 통제할 수 없습니다.

참고: 출금 요청 ↗ · 자금 동결 ↗

서명과 출금 완료

정책 연동은 설계 흐름

현재 Wallet 서버는 실제 정책 서버와 연결되지 않아 동기 자동 승인합니다. 아래의 정책 심사·서명 인가 흐름은 연동 설계이며, 실제 연결과 거부·실패 동작 검증이 필요합니다.

참고: 정책 결과와 현재 구현 ↗

  1. 파트너가 출금 업무를 승인합니다

    고객 귀속 금액과 자체 AML·FDS 기준을 확인하고 요청합니다. 이 판단과 SDK 정책 판단은 서로 다른 책임입니다.

  2. SDK가 정책 판단을 받습니다

    정책 엔진은 비동기로 평가하고 허용된 요청에 일회용 서명 인가를 발급합니다. 거부되면 서명 인프라에 제출하지 않습니다.

  3. 서명 직전에 승인된 내용을 대조합니다

    목적지·금액 등 실제 서명 대상이 인가와 맞고 미만료·미소비 상태여야 진행합니다.

  4. 이벤트와 조회로 완료를 확인합니다

    WITHDRAWAL_INITIATED는 시작, WITHDRAWAL_FINALIZED는 완료, WITHDRAWAL_FAILED는 실패입니다. 시작 또는 트랜잭션 감지만으로 완료 처리하지 않습니다.

GET요청 예시
GET /api/v1/accounts/{accountId}/withdrawals/{withdrawalId}
X-API-KEY: <발급받은_API_키>

참고: 출금 (Withdrawal) ↗ · 웹훅(Webhook) ↗ · 서명 게이트 ↗

실패와 재조회

결과를 알 수 없으면 withdrawalId로 조회하거나 계정의 출금 목록에서 해당 요청을 찾습니다. 고객 출금에는 referenceId 전용 조회 API가 없습니다. 목록 조회 조건과 중복 생성 처리는 상세 명세를 확인합니다.

비활성 Account의 고객 출금은 404로 거부됩니다. 오입금 반환은 입금 당시의 송신 주소 기록이 있어야 요청할 수 있습니다. 다른 주소로 반환하는 경로는 아직 정해지지 않았습니다.

반환 승인 경로 미확정

자금 흐름 문서는 반환에 운영자 승인을 요구하지만, 정책 문서는 일반 admin_action 접수를 403으로 거부한다고 설명합니다. 반환 요청이 실제로 어느 승인 경로를 거치는지 확인이 필요합니다.

참고: 출금 (Withdrawal) ↗ · 승인 게이트 ↗

정책 거부 상태

계약상 정책 거부는 FAILED / SCREENING_REJECTED로 읽습니다. 출금 정책 거부 전용 오류 코드는 명세에 없고, 현재 자동 승인 구현에서는 거부 분기에 도달하지 않습니다.

참고: 정책 결과와 현재 구현 ↗
