입금 주소 발급

계정을 생성한 뒤 토큰을 선택해 AccountWallet을 발급합니다. 반환된 주소가 고객의 입금 주소입니다.

환경 준비

Workspace, Network, Tenant, API 키, Token, WorkspaceVault는 플랫폼 운영자가 먼저 준비해야 합니다. 실제 API 호스트와 온보딩 절차도 운영자에게 확인합니다.

예시의 키와 ID를 발급받은 값으로 바꿔 호출합니다. 인증 헤더는 X-API-KEY이며, Workspace와 Tenant는 API 키에 연결된 범위가 적용됩니다.

키 전달

API 키의 비밀 값은 승인 후 한 번만 표시됩니다. 발급받을 때 비밀 저장소에 보관해야 합니다.

참고: 첫 요청 ↗ · 표면과 인증 ↗

계정 생성

POST요청 예시
POST /api/v1/accounts
X-API-KEY: <발급받은_API_키>
Content-Type: application/json

{
  "referenceId": "user-8f21c0"
}

201 응답의 계정 ID를 파트너 사용자와 연결해 저장합니다. 같은 Tenant에서 이미 사용한 referenceId는 400입니다. 응답을 놓쳤다면 다음 조회로 기존 계정을 확인합니다.

GET요청 예시
GET /api/v1/accounts?referenceId=user-8f21c0
X-API-KEY: <발급받은_API_키>

참고: 계정 생성 ↗ · 계정 referenceId 조회 ↗

토큰 선택과 지갑 생성

GET요청 예시
GET /api/v1/tokens
X-API-KEY: <발급받은_API_키>

활성 Token·Network 목록에서 실제 tokenId를 선택합니다. 지갑 생성에는 SDK가 반환한 accountId를 넣습니다.

POST요청 예시
POST /api/v1/accounts/{accountId}/account-wallets
X-API-KEY: <발급받은_API_키>
Idempotency-Key: <요청_식별자>
Content-Type: application/json

{
  "tokenId": "<선택한_tokenId>"
}

201 응답의 Wallet ID와 주소를 저장합니다. 사용자는 해당 네트워크·토큰으로 이 주소에 송금합니다.

지갑 생성 재시도

Idempotency-Key는 필수지만 현재 서버에서 사용하지 않습니다. 응답을 받지 못했으면 지갑 목록부터 조회합니다. 생성 여부를 확인하기 전에는 같은 요청을 다시 보내지 않습니다.

GET요청 예시
GET /api/v1/accounts/{accountId}/account-wallets
X-API-KEY: <발급받은_API_키>

참고: 첫 요청 ↗ · 계정 지갑 생성 ↗

입금 확인

  1. 주소 발급 완료

    계정·Wallet·Token·주소 매핑을 저장하고 고객에게 네트워크와 주소를 전달합니다.

  2. 입금 관측 대기

    고객이 온체인으로 송금하면 SDK가 감지합니다. 파트너가 호출하는 “입금 생성 API”는 없습니다.

  3. 입금 확정 후 처리

    웹훅 또는 입금 조회로 상태를 확인합니다. 확정된 입금도 SDK 내부에서는 동결되므로 별도의 Sweep 판단이 필요합니다.

GET요청 예시
GET /api/v1/accounts/{accountId}/deposits
X-API-KEY: <발급받은_API_키>

참고: 첫 요청 ↗ · 입금 (Deposit) ↗
