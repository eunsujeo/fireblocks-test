정책 평가와 서명

정책 엔진이 요청을 평가해 일회용 인가를 발급합니다. 서명 직전에는 실제 트랜잭션이 인가 내용과 일치하는지 검사합니다.

이 페이지 목차
독립 정책 엔진을 두는 이유다이어그램으로 보는 평가와 서명평가와 서명 검증요청 접수와 결과 통지예제 1 — 등록된 개인 지갑으로 출금예제 2 — 승인 후 거래가 바뀌는 경우인가 유효 시간운영자 승인정책 작성과 결과 확인

독립 정책 엔진을 두는 이유

서비스 수준의 정책 판단과 승인 이력을 독립적으로 관리하고, product service가 고위험 업무를 단독 실행하지 못하게 하기 위한 설계입니다. Policy Server가 업무 실행 허가를 판단하고, Fireblocks 거래의 서명 직전에는 Co-Signer Callback으로 그 허가를 강제합니다. Fireblocks 자체 정책과 추가 승인 요건도 함께 충족해야 합니다.

도입 근거와 역할

설계 근거의미
메인 설계 문서 2.3 · 운영 전제Fireblocks policy와 별개로 서비스 수준의 정책 판단 및 승인 이력을 관리합니다.
후속 설계 문서 · 2026-06-09 결정 로그Policy-Gated Operation Model을 도입해 product service가 고위험 업무나 Fireblocks transaction을 단독 실행하지 않고 Policy Server의 최종 업무 허가를 받게 합니다.
리스크 표 · Policy Server 우회product service가 거래를 직접 생성할 수 있더라도, Co-Signer Callback이 Policy Server 검증을 통과하지 않으면 서명되지 않아야 합니다.
메인 설계 문서 · Policy-Gated Operation Model외부 승인 주체는 Fireblocks 정책엔진의 추가 승인 요건입니다. JV cosigner가 allow해도 Fireblocks의 승인 요건이 부족하면 거절될 수 있습니다.

근거: 사용자가 제공한 메인·후속 설계 문서 발췌를 요약했습니다. 해당 설계 원문은 이 SDK 보관본에 포함되어 있지 않습니다.

거래 생성과 서명 허가는 별개입니다

예를 들어 product service가 Policy Server를 거치지 않고 출금 거래를 직접 생성했다고 가정합니다. 서명 단계에서 PEP가 실제 서명 대상을 전달하고, Orchestrator가 유효한 인가와의 일치를 검증해야 합니다. 인가가 없거나 거래 내용이 다르면 서명을 거부해야 합니다. 이 통제가 성립하려면 대상 거래의 서명 경로에 해당 콜백 검증이 필수로 연결되어야 합니다.

서비스 정책·서명 대조Fireblocks 정책·승인 요건결과
통과충족두 정책 계층의 조건을 충족합니다. 나머지 서명·실행 조건도 통과해야 거래를 진행할 수 있습니다.
거부 또는 유효한 인가 없음충족콜백 검증에서 서명을 차단해야 합니다.
통과추가 승인 부족 또는 정책 거부서비스의 허용만으로 진행할 수 없습니다.

두 계층의 허용은 모두 필요한 조건입니다. Policy Server의 최종 업무 허가는 Fireblocks의 정책 결정을 덮어쓰지 않으며, 어느 한쪽의 허용도 온체인 거래 완료를 보장하지 않습니다.

벤더 종속 완화는 별도의 설계 목적입니다

리스크 표의 Custody vendor lock-in 항목은 Fireblocks의 운영 편의성을 활용하면서 Wallet Server에 custody provider 추상화 계층을 두도록 합니다. 이 구조는 서비스 정책을 벤더와 분리하는 데 도움이 됩니다. Dfns 등 다른 제공자에서도 같은 통제를 유지하려면 해당 제공자의 서명·승인 경로에 인가 검증을 연결해야 하며, 추상화 인터페이스만으로 우회 차단이 완성되지는 않습니다.

이 절은 도입 의도와 요구되는 통제를 설명합니다. 보관된 SDK의 실제 정책 연동 상태와 현재 제약은 아래에서 함께 확인합니다.

다이어그램으로 보는 평가와 서명

첫 그림은 업무 허가를 발급하는 과정이고, 두 번째는 실제 거래의 서명 조건입니다. 보관된 v1.1.0 문서에서는 Wallet 서버와 실 정책 서버가 아직 연결되지 않았으므로, 아래 그림은 정책 연동 설계를 설명합니다.

1. 정책 평가 → 일회용 인가 → 거래 제출

Orchestrator가 처리를 조율하고 PDP가 판단합니다. 자료가 부족하면 PIP로 필요한 사실을 수집한 뒤 재평가합니다. 보관된 버전의 수집 소스는 주소 소유 상태이며, 그림은 현재 서명 연산의 allow·deny·자료 보완 경로를 표시합니다.

2. 콜백 검증 + Fireblocks 정책 → 서명

PEP가 콜백을 인증하고 Orchestrator가 실제 거래와 인가를 대조합니다. 서비스 콜백 통과와 Fireblocks 자체 정책·승인 요건 충족이 모두 필요합니다. 아래 AND는 두 조건의 논리적 결합이며, Fireblocks 내부 처리 순서를 지정하지 않습니다.

평가와 서명 검증

설계 흐름과 현재 연결 상태

아래는 정책 연동 설계입니다. 보관된 v1.1.0 문서는 Wallet 서버와 실 정책 서버가 아직 연결되지 않았고 현재 동기 자동 승인한다고 명시합니다. 이 흐름을 현재 배포에서 검증된 처리로 보지 않습니다.

참고: 정책 결과와 현재 구현 ↗

요청 시점에는 정책을 평가해 인가를 발급하고, 서명 직전에는 실제 거래가 그 인가와 일치하는지 검사합니다. 밑줄이 있는 용어는 마우스를 올리거나 키보드로 선택하거나 터치하면 설명을 볼 수 있습니다.

역할맡는 일
접수·정규화·자료 수집·재평가를 조율하고, 인가 저장·서명 직전 대조·일회용 소비를 맡습니다.
주어진 입력에 룰을 적용해 판단합니다. 직접 외부 시스템을 조회하지 않습니다.
룰이 요구하는 주소 소유 등 사실을 가져오는 Orchestrator의 어댑터 계층입니다.
Co-Signer 콜백을 받아 JWT를 검증하고 서명 대상을 추출합니다. 대조·소비는 Orchestrator에 맡깁니다.

1단계 — 정책 평가와 인가 발급

  1. 접수하고 정규화합니다

    Wallet 서버가 POST /request로 판단을 요청하면 Orchestrator는 202와 판단 요청 ID를 돌려줍니다. 이후 비동기로 출발 지갑의 소유·체인을 해석하고 승인할 거래의 고정 내용을 정규화합니다.

  2. 필요한 사실을 수집하고 평가합니다

    PDP가 적용할 룰을 평가합니다. 자료가 부족하면 need_more_data를 반환하고, Orchestrator가 PIP로 자료를 수집한 뒤 전체 입력으로 재평가합니다. 보관된 버전의 평가 루프 수집 소스는 address_ownership입니다.

  3. 허용하면 일회용 인가를 발급합니다

    allow이면 승인 내용·유효 시간·수수료 상한과 함께 signingAuthorizationId를 저장하고 결과 이벤트를 발행합니다. deny이면 거부 이벤트로 끝나며 서명 인프라에 제출하지 않습니다.

  4. 인가 ID와 함께 거래를 제출합니다

    Wallet 서버는 승인 이벤트를 받아 서명 인프라에 거래를 제출합니다. 문서의 Fireblocks 경로에서는 externalTxId에 인가 ID를 연결합니다. 이 ID는 조회 단서이며, 거래 내용의 검증을 대신하지 않습니다.

2단계 — 실제 서명 대상 대조와 소비

  1. 서명 직전 콜백을 받습니다

    Co-Signer가 PEP에 JWT와 실제 서명 대상을 보냅니다. PEP는 인증·내용 추출 후 Orchestrator에 대조를 요청합니다.

  2. 승인 내용과 실제 거래를 맞춥니다

    Orchestrator는 인가의 존재·만료·소비 여부, 출발 지갑과 실제 서명할 내용을 확인합니다. EVM 트랜잭션은 고정 필드와 nonce·수수료 등 서명 시점 값으로 재구성하고 수수료 상한도 대조합니다.

  3. 통과한 인가를 한 번 소비합니다

    대조에 성공하면 인가를 원자적으로 소비하고 PEP가 승인 응답에 서명합니다. 거부되면 Co-Signer는 서명하지 않습니다. 이 콜백 경로에서는 주소록·AML 등 외부 시스템을 다시 호출하지 않습니다.

  4. 서명·방송 후 거래 결과를 추적합니다

    서비스 인가 대조와 Fireblocks 자체 정책·추가 승인 요건을 모두 충족하고 나머지 실행 조건도 통과하면 서명 인프라가 거래를 서명·방송합니다. 정책 승인이나 인가 소비는 온체인 완료를 뜻하지 않습니다. Wallet 서버는 이후 거래 상태와 웹훅으로 최종 결과를 전달합니다.

정책 커널의 pending은 추가 이행 조건을 기다리는 결정입니다. 다만 현재 서명 연산에는 obligation 루프가 없어 정족수 승인을 요구할 수 없다고 문서가 명시합니다. 관리자 2명 승인이 위 흐름에 이미 연결됐다고 해석하지 않습니다.

예제 1 — 등록된 개인 지갑으로 출금

설명을 위해 custody vault에서 등록된 개인 지갑 A로 100 USDC를 출금한다고 가정합니다. 아래 JSON은 문서에 실린 실제 시드 정책이며 출금 API 요청 본문은 아닙니다. 주소 A와 금액 100 USDC는 이해를 돕기 위한 예시입니다.

{
  "id": "withdrawal/allow-evm-external-address",
  "effect": "allow",
  "scope": {
    "all": [
      { "field": "operation", "op": "eq", "value": "value_transfer" },
      { "field": "chain.family", "op": "eq", "value": "evm" },
      { "field": "destination.type", "op": "eq", "value": "external_address" },
      { "field": "source_vault.kind", "op": "eq", "value": "custody" }
    ]
  },
  "when": { "field": "address_ownership.status", "op": "eq", "value": "active" }
}

scope는 이 룰을 적용할 요청을 고르고, when은 허용 조건을 검사합니다. 출금은 정규화 과정에서 value_transfer가 됩니다. 주소 상태는 요청자의 주장 대신 PIP가 읽은 address_ownership.status로 확인합니다.

상황이 룰의 판정
EVM·custody 출발·외부 주소 A·등재 상태 active허용
같은 요청이지만 주소가 unregistered조건 불성립으로 거부
주소가 회수돼 revoked조건 불성립으로 거부
주소 상태를 아직 수집하지 못함need_more_data → 수집 후 재평가

다른 룰도 적용된다면 최종 결정은 결합 규칙을 따릅니다. 이 시드 룰에는 송금액 100 USDC를 제한하는 조건이 없습니다. 문서는 자산별 금액 상한 조건은 token_catalog 수집이 없어 현재 작성할 수 없다고 설명합니다.

예제 2 — 승인 후 거래가 바뀌는 경우

앞선 평가로 “지갑 A에게 100 USDC”가 승인되었다고 가정합니다. 서명 직전에는 PEP가 전달한 실제 서명 대상과 저장된 인가 내용을 Orchestrator가 대조합니다.

실제 서명 요청결과
승인된 A에게 100 USDC·올바른 서명 지갑·수수료 상한 이내·유효한 미소비 인가인가 소비 후 승인
목적지가 B로 변경됨거부
금액이 1,000 USDC로 변경됨거부
다른 지갑의 키로 서명하려 함거부
수수료 상한 초과거부
인가 부재·만료·이미 소비됨거부

EVM 수수료 상한은 재구성 검증을 통과한 트랜잭션에서 gasLimit × maxFeePerGas로 유도합니다. 이는 최대 수수료이며 송금액 상한과는 별개입니다. 체인별 상한이 없으면 무제한으로 허용하지 않고 거부합니다.

참고: 정규화·서명 대상 대조 ↗ · 서명 상한 대조 ↗

인가 유효 시간

서명 인가의 TTL은 기본·하한 20분, 상한 60분입니다. 정책을 새로 배포해도 이미 발급된 인가는 TTL까지 유효합니다.

서명 콜백은 외부 데이터를 다시 읽지 않습니다. 따라서 주소를 긴급 차단하거나 정책을 바꿨을 때 기존 인가를 어떻게 취소·차단할지는 별도로 확인해야 합니다. 일회용 인가 소비가 파트너 원장 반영까지 한 번만 일어나게 해주는 것은 아닙니다.

자금 이동의 서명 게이트정책 판단과 실제 서명 대조를 연결하는 2단계
일반 admin_action 승인 게이트접수 표면에서 403으로 거부. 승인 뒤 권한 적용·발행 경로도 아직 없음
현재 룰 변경 승인초안 revision의 내용 해시에 표를 결속하는 별도 maker-checker. 발행과 활성화는 각각 호출
현재 역할 부여초대 표면에서 직접 인가. 제안자·승인자를 나누는 단계는 없음
admin_action 미지원

통합 admin_action 승인 경로는 아직 동작하지 않습니다. 운영자 승인이 필요한 액션은 현재 제공되는 개별 경로와 지원 범위를 확인해야 합니다.

Wallet Admin 승인 API의 현재 한계

Approvals API 세 개는 고정 응답을 냅니다. 승인 게이팅을 거치는 엔드포인트도 현재 APPROVED·DENIED만 내며 quorum은 null입니다. 반환·해제의 정족수 승인이 동작한다고 전제하지 않습니다. Policy API의 통합 admin_action 미지원과 구분해 확인합니다.

정책 작성과 결과 확인

서명 게이트 → 룰 쓰기 → 예시 정책 → 룰 저작과 발행 → 결과 읽기 순서로 읽습니다. 엔진 내부 동작은 별도 참고 문서에서 확인합니다.

항목확인할 내용
룰 필드요청 필드는 scope·when에서, 평가 중 PIP가 수집하는 필드는 when에서 사용합니다. 참조 가능 필드 표는 원문의 생성된 카탈로그를 확인합니다.
시드 집금 정책EVM·서비스 주체·deposit → custody 내부 이동을 허용합니다. 조건은 없습니다. 이 종류 구분만으로 핫·콜드·고객·회사 용도 태그 통제가 완성되지는 않습니다.
승인·발행승인은 검증된 revision의 내용 해시에 묶입니다. 내용을 고치면 다시 검증·승인해야 하며 발행과 활성화는 별도 액션입니다.
현재 제약서명 연산 정족수 루프와 자산별 금액 상한 조건은 현재 사용할 수 없다고 명시합니다. resource_limit_per_tx는 건당 수수료 상한이며 송금액 상한과 다릅니다.
