BCM API·Webhook·BAT·Admin이 운영 중 남기는 로그의 공통 JSON 계약과 중앙 수집 책임, 보존·삭제 기준을 정한다.
일반 운영 로그를 감사 원장이나 Webhook·거래 원문의 대체물로 쓰지 않으며 수집 제품과 전송 기술은 이 문서에서 결정하지 않는다.

## 목적과 비목적

이 문서의 목적은 다음과 같다.

- 서비스마다 다른 평문 로그를 하나의 구조화 JSON 계약으로 통일한다.
- 요청과 거래, Webhook, 이벤트, 배치 실행을 안전한 식별자로 연결한다.
- 애플리케이션과 중앙 수집·보관 영역의 책임을 나눈다.
- 민감정보를 수집 전에 차단하고 로그 분류별 보존·삭제 절차를 고정한다.
- 로그 유실·변조·무단 조회와 보존 기한 초과를 감지할 검증 기준을 둔다.

다음은 이 문서에서 결정하지 않는다.

- 중앙 수집 제품, agent, 전송 프로토콜, 검색 엔진과 archive 제품
- 모니터링 지표·경보 임계값과 당직 체계
- 감사 원장의 물리 스키마와 외부 감사 보관소
- `bcm_tx_l`·`bcm_whk_l`·`bcm_outbox_l`·`bcm_raw_tx_l` 등 업무 DB 원문의 보존 기간
- 법무·보안 승인이 필요한 로그 분류별 실제 보존 일수

## 기록의 종류와 정본

| 구분 | 목적 | 정본 | 이 문서의 보존 정책 적용 |
|---|---|---|---:|
| 운영 로그 | 장애 분석, 처리 흐름·지연·재시도 확인 | 중앙 로그 저장소 | O |
| 보안 이벤트 로그 | 인증·권한·입력 검증 실패, 보안 설정 변경 탐지 | 접근이 제한된 중앙 로그 저장소 | O |
| 감사 원장 | 운영 변경의 요청·승인·실행·외부 대조 재구성 | 추가 전용 업무 DB 원장 | X |
| Webhook·거래 원문 | 재처리와 거래 상태 대사 | BCM DB의 인박스·거래·원본 테이블 | X |
| 로컬 테스트 artifact | 개발자 PC·CI 실행 진단 | `build/system-test/<runId>/` | X |

운영 로그는 상태의 증거가 아니라 관찰 기록이다. 거래 완료, 이벤트 발행, 정책 활성화와 비상 조치 완료 여부는 각 업무 원장과 외부
재조회 결과로 판단한다. 중앙 로그에 같은 사실이 있다는 이유로 누락된 업무 원장이나 감사 action을 보완한 것으로 간주하지 않는다.

감사 원장은 [Admin](08-bcm-admin.md)의 추가 전용·영구 보존 계약을 따른다. 운영 로그 수집 실패는 일반 업무 처리를 막지 않지만,
감사 기록이 필수인 운영 mutation은 감사 원장을 기록할 수 없으면 실행하지 않는다.

## JSON 출력 계약

운영 프로세스는 한 줄에 JSON 객체 하나를 출력한다. 객체 바깥에 시각, level, logger 이름을 덧붙이지 않고 예외도 같은 객체 안에
구조화한다. 모든 서비스가 `bcm-log-v1`을 사용하며 호환되지 않는 변경은 새 schema version으로 올린다.

```json
{
  "schemaVersion": "bcm-log-v1",
  "occurredAt": "2026-08-21T04:10:12.123Z",
  "level": "INFO",
  "service": "bcm-webhook",
  "environment": "production",
  "eventCode": "WEBHOOK_PROCESSING_COMPLETED",
  "message": "Webhook 처리를 완료했습니다.",
  "requestId": "req-6f3d7d",
  "identifiers": {
    "vendorTxId": "vtx-82a4",
    "txHash": "0x8d21...c941",
    "eventId": "evt-0198"
  },
  "outcome": "SUCCESS",
  "durationMs": 37
}
```

### 공통 필드

| 필드 | 필수 | 형식·규칙 |
|---|---:|---|
| `schemaVersion` | O | 현재 값 `bcm-log-v1`. 수집 시 해석 계약을 선택하는 값 |
| `occurredAt` | O | 애플리케이션이 사건을 관찰한 UTC ISO 8601 시각. 밀리초 포함 |
| `level` | O | `TRACE/DEBUG/INFO/WARN/ERROR` |
| `service` | O | 배포 단위의 고정 코드. 초기 값은 `bcm-api/bcm-webhook/bcm-bat/bcm-admin` |
| `environment` | O | 배포가 주입한 고정 환경 코드. 요청값에서 만들지 않음 |
| `eventCode` | O | 사건 종류를 나타내는 대문자 snake case 고정 코드 |
| `message` | O | 운영자가 읽는 안전한 고정 문장. 식별자·원문·예외 메시지를 합치지 않음 |
| `requestId` | 조건부 | HTTP·비동기 작업의 최초 요청 식별자를 알고 있을 때 기록 |
| `identifiers` | 조건부 | 실제 생성·수신한 상관 식별자만 기록. 없는 값을 만들거나 `null`로 채우지 않음 |
| `outcome` | 조건부 | 결과가 있는 사건은 `SUCCESS/FAILURE/DEFERRED/UNKNOWN` 중 하나 |
| `durationMs` | 조건부 | 끝난 작업의 0 이상 정수 경과 시간. 시작·진행 사건에는 넣지 않음 |
| `error` | 조건부 | 실패를 분류하는 안전한 구조체. `ERROR` level이라고 반드시 stack trace를 싣지는 않음 |

`eventCode`는 문장이나 외부 상태값이 아니다. 서비스 코드에 등록한 제한된 목록으로 관리하고 동적 문자열을 만들지 않는다. 같은 사건은
배포 버전이 달라도 같은 코드를 쓰며 의미가 달라지면 새 코드를 추가한다. level과 message를 바꿔 기존 코드의 뜻을 재사용하지 않는다.

### 상관 식별자

`identifiers`에는 다음 키만 허용한다. 새 키가 필요하면 schema와 이 표를 먼저 바꾼다.

| 키 | 용도 |
|---|---|
| `externalTxId` | DAW-CORE가 지시한 외부 거래 식별자 |
| `submissionId` | 제출 시도 식별자 |
| `vendorTxId` | 벤더 거래 식별자 |
| `txHash` | 실제 온체인 거래 hash |
| `eventId` | 발행 이벤트 식별자 |
| `executionId` | 정책·컨트랙트·비상 운영 실행 식별자 |
| `jobRunId` | BAT 실행 식별자 |

연결 순서는 `requestId → externalTxId/submissionId → vendorTxId → txHash → eventId → executionId/jobRunId`다. 한 로그에 모든 값을
반복하지 않고 해당 단계에서 이미 알고 있는 값만 기록한다. 로그 조회 화면은 식별자로 앞뒤 사건을 연결하되 값이 없다는 이유로 추정값을
만들지 않는다.

### 오류 구조

```json
{
  "error": {
    "code": "VENDOR_REQUEST_TIMEOUT",
    "type": "HttpTimeoutException",
    "retryable": true,
    "summary": "벤더 응답 제한 시간을 초과했습니다."
  }
}
```

- `error.code`는 애플리케이션이 정한 안정적인 분류 코드다.
- `error.type`은 내부 예외 class의 단순 이름이며 패키지·소스 경로를 포함하지 않는다.
- `error.summary`는 운영자용 안전 문장이다. 벤더 응답 본문과 `exception.message`를 그대로 복사하지 않는다.
- stack trace가 필요하면 `ERROR` 사건의 별도 제한 필드로만 보낸다. 요청·응답 원문이나 Secret이 섞이지 않았음을 검증하고 일반 조회
  권한과 분리한다.
- 같은 실패를 여러 계층에서 중복 기록하지 않는다. 처리·재시도 여부를 결정한 경계가 한 번 기록하고 하위 예외는 원인 chain으로만 남긴다.

## 기록 허용선

### 기본 허용

- 고정 service·environment·eventCode와 level
- 네트워크 코드, 등록 자산 symbol, 내부 상태 enum
- 처리 건수, 대기·격리 건수, 경과 시간과 재시도 횟수
- `requestId`와 위 표의 거래·이벤트·실행 상관 식별자
- 외부 HTTP의 method, 논리 endpoint ID, 응답 status code
- 애플리케이션이 분류한 안전한 오류 코드·요약

외부 HTTP 경로는 실제 URL 대신 `FIREBLOCKS_CREATE_TRANSACTION`, `RPC_RECEIPT_QUERY` 같은 논리 endpoint ID로 기록한다. query string,
credential이 들어간 URL, 내부 IP와 host 전체 값은 기록하지 않는다.

### 조건부 허용

| 값 | 규칙 |
|---|---|
| BCM `accountId` | 고객 귀속이 필요 없는 일반 로그에서는 제외. 장애 조사 전용 권한에서만 사용 |
| 블록체인 주소 | 기본 로그에서는 앞뒤 일부만 남기거나 별도 조회로 연결. 전체 주소 검색 필요성은 보안 승인 대상 |
| 직원번호·부점코드 | 감사 원장에만 기록. 일반 운영 로그에는 넣지 않음 |
| client IP·User-Agent | 보안 이벤트 목적과 보존 기간을 승인한 경우에만 기록 |
| 파일 경로 | 애플리케이션이 정한 논리 artifact 이름만 허용. 사용자 입력과 절대경로는 제외 |
| stack trace | 제한된 오류 조회 권한과 민감정보 검증이 있을 때만 허용 |

### 기록 금지

- API key, Secret, password, JWT, 세션·Cookie, `Authorization` 헤더
- private key, PEM·key 내용, Webhook 서명
- Webhook raw payload와 HTTP 요청·응답 body
- DB connection string, credential이 포함된 URL과 환경변수 전체 dump
- 이름·전화번호·이메일·신분증 정보 등 PII
- 고객 참조키와 트래블룰 PII 원문
- 임의 SQL, 전체 설정 객체, 프로세스 환경 전체

마스킹은 기록 금지 값을 저장해도 된다는 뜻이 아니다. 조사에 필요하지 않으면 필드를 만들지 않는다. 일부 표시가 필요한 주소처럼
조건부 허용한 값에만 고정 마스킹 규칙을 사용한다. 애플리케이션에서 제거한 뒤 중앙 수집 경계에서도 금지 키와 값 패턴을 다시 검사한다.

## level과 필수 사건

| level | 사용 기준 | 운영 기본값 |
|---|---|---|
| `TRACE` | 개발 중 함수 단위 추적 | 운영 출력 금지 |
| `DEBUG` | 승인된 기간의 상세 진단 | 운영 기본 비활성 |
| `INFO` | 정상 시작·완료와 중요한 상태 전이 | 수집 |
| `WARN` | 자동 복구·재시도 중이며 즉시 실패는 아닌 상태 | 수집·집계 |
| `ERROR` | 요청·작업 실패, 격리, 복구 불가능 또는 운영 개입 필요 | 수집·경보 연결 |

다음 사건은 level 설정으로 끌 수 없다.

- 프로세스 시작·정상 종료·비정상 종료와 readiness 상실·회복
- 외부 요청 최종 실패, timeout 소진과 rate limit 장기화
- Webhook 서명 검증 실패, replay·중복·역순 판정과 격리
- 인박스·outbox·Kafka 처리 최종 실패와 poison 이동
- 거래 제출·확정·실패·boost·sweep의 업무 상태 전이
- BAT 시작·완료·부분 실패·lease 상실
- Admin 인증·권한·CSRF·Origin 검증 실패와 위험 작업 접수 결과
- 로그 수집 중단, schema 파싱 실패, 금지 필드 탐지와 삭제 배치 실패

정상 polling 성공처럼 반복량이 큰 사건은 매번 기록하지 않고 상태 변화나 주기 요약으로 남긴다. 운영 조사에 필요한 식별자와 실패는
sampling하지 않는다. 동일 오류 억제가 필요하면 최초 발생, 억제 건수, 마지막 발생 시각과 회복 사건을 남긴다.

## 중앙 수집 책임

```text
BCM 프로세스 → JSON 로그 출력 → 플랫폼 수집 경계 → 중앙 검색·보관 영역
```

| 책임자 | 책임 |
|---|---|
| BCM 애플리케이션 | JSON schema 준수, 사건 분류, 상관 식별자 전달, 민감정보 사전 제거 |
| 플랫폼 수집 영역 | 로그 수신·전달, 재시도·완충, schema 검증, 배포 정보 보강, 금지 필드 2차 차단 |
| 중앙 로그 운영자 | 검색·접근 권한, 보존·삭제, archive, 용량·유실 감시와 복구 |
| 보안·법무 | 조건부 필드 승인, 보존 기간·법적 보류, 조회·반출 기준 승인 |
| 서비스 운영자 | eventCode 목록, 필수 사건 누락과 경보 연결 검증 |

애플리케이션은 중앙 제품의 client나 저장소 API에 직접 의존하지 않는다. 중앙 수집 장애가 업무 thread를 장시간 점유하거나 업무 DB
transaction을 롤백하게 해서는 안 된다. 대신 전달 실패·buffer 포화·drop 수와 마지막 정상 전달 시각을 별도 운영 신호로 노출한다.

중앙 수집 경계는 다음을 보장해야 한다.

- 전송 구간 암호화와 송신 service 신원 확인
- 재시작·일시 장애를 견디는 제한된 완충과 재전송
- 용량 초과 시 무음 삭제 금지. drop 수·대상 기간·분류를 경보와 사고 기록으로 남김
- 동일 로그의 재전송 허용. 중앙 저장소는 중복을 숨기더라도 원본의 사건 의미를 바꾸지 않음
- 수집 시각과 원본 `occurredAt`을 구분해 clock drift와 지연을 관찰
- `schemaVersion` 미지원·JSON 파싱 실패를 별도 격리하고 정상 로그로 추정하지 않음

## 접근·보호

- 운영·보안·감사 역할의 조회 범위를 분리하고 production 로그는 최소 권한으로 연다.
- 로그 조회·다운로드·보존 연장·삭제 정책 변경을 별도 감사 사건으로 남긴다.
- 중앙 저장소와 archive는 전송 중·저장 시 암호화하고 운영 애플리케이션 계정에 수정·삭제 권한을 주지 않는다.
- 보안 이벤트와 장기 archive는 변경·삭제 탐지 수단을 두고 검증 결과를 정기적으로 남긴다.
- 다운로드 파일에도 원본과 같은 보존 만료일을 적용한다. 개인 PC나 작업 티켓에 무기한 복사하지 않는다.
- 장애 조사 종료 뒤 임시 권한·추출본·DEBUG 설정을 회수하고 회수 결과를 기록한다.

## 보존·삭제 정책

### 분류

| 분류 | 대상 | 보존 원칙 | 기간 상태 |
|---|---|---|---|
| `EPHEMERAL` | 승인된 운영 DEBUG와 임시 상세 진단 | 조사 종료 후 가장 먼저 삭제 | 미확정 |
| `OPERATIONAL` | INFO·WARN 중심의 일반 운영 로그 | 일상 장애 분석 기간만 검색·보관 | 미확정 |
| `ERROR_SECURITY` | ERROR, 보안 검증 실패와 수집 무결성 사건 | 일반 운영 로그보다 길게 보존 | 미확정 |
| `AUDIT` | 운영 변경 요청·승인·실행 원장 | 일반 로그 저장소가 아닌 추가 전용 원장에 영구 보존 | 확정 |

실제 기간은 중앙 로그 운영 전 보안·법무·서비스 책임자가 함께 승인한다. 기간을 정할 때 하루 평균·최대 로그량, 장애 발견까지 걸리는
시간, 사고 조사 기간, 계약·규제 의무, 백업 주기와 삭제 가능 여부를 증적으로 남긴다. 비용만으로 보안·감사 보존 기간을 줄이지 않는다.

각 로그에는 수집 시 분류와 정책 version을 붙이고 중앙 저장소가 `retentionClass`, `retentionPolicyVersion`, `expiresAt`을 계산한다.
이 세 값은 애플리케이션 JSON 계약에 넣지 않는다. 애플리케이션이 자기 로그의 삭제 시각을 정하지 않게 하기 위해서다.

### 삭제와 법적 보류

- 만료 전 삭제와 만료 후 무기한 보관을 모두 실패로 본다.
- 삭제 범위에는 검색 저장소, archive, backup, 복원본과 다운로드·추출본이 포함된다.
- 삭제 작업은 대상 기간·분류·건수, 성공·실패와 재시도 결과를 감사 가능한 요약으로 남긴다. 삭제한 로그 원문을 증적으로 복사하지 않는다.
- 법적 보류는 승인자, 사유·사건 번호, 대상·시작·재검토 시각을 기록하고 일반 만료보다 우선한다.
- 법적 보류 해제 뒤에는 원래 만료일을 다시 계산해 이미 만료된 자료를 다음 삭제 작업에서 정리한다.
- 정책 변경은 새 version부터 적용한다. 기존 자료를 소급 연장하거나 단축하려면 별도 승인과 영향 분석이 필요하다.

업무 DB 원문 보존은 이 정책과 독립적으로 결정한다. 운영 로그가 만료돼도 업무 원장의 법정·업무 보존 의무는 바뀌지 않으며, 반대로
업무 DB에 원문이 남아 있다는 이유로 운영 로그를 승인 기간보다 오래 보관하지 않는다.

## 변경·검증 계약

### 구현 테스트

- 모든 필수 사건을 JSON Schema로 검증하고 알 수 없는 최상위 필드와 잘못된 enum을 거부한다.
- 줄바꿈·제어문자·큰 입력을 넣어도 로그 한 건의 경계를 벗어나거나 새 사건을 위조하지 못하게 한다.
- Secret·JWT·Webhook 서명·raw payload·PII fixture가 로그와 stack trace에 나타나지 않음을 검사한다.
- 요청→거래 제출→Webhook→이벤트 발행을 식별자로 연결하고 존재하지 않는 ID를 만들지 않음을 확인한다.
- 같은 예외를 계층마다 중복 기록하지 않고 재시도·최종 실패·회복 사건이 구분되는지 확인한다.
- 운영 설정에서 TRACE가 나오지 않고 DEBUG 활성화에 만료·승인 정보가 필요한지 확인한다.

### 운영 검증

- 중앙 수집을 중단했다가 복구해 업무 처리는 계속되고 유실·지연·drop이 탐지되는지 훈련한다.
- 지원하지 않는 schema version과 깨진 JSON을 격리하고 운영자에게 알리는지 확인한다.
- 서비스별 입력 건수와 중앙 저장 건수를 닫힌 시간 구간으로 대조한다.
- 권한 없는 조회·다운로드·정책 변경이 거부되고 허용된 접근은 감사되는지 확인한다.
- 보존 만료, 삭제 실패, 법적 보류 설정·해제를 비운영 자료로 반복 검증한다.
- archive 복원본도 원래 접근권한과 만료일을 유지하는지 확인한다.

## 도입 순서

1. `bcm-log-v1` JSON Schema와 서비스별 `eventCode` 목록을 확정한다.
2. 공통 logger adapter와 민감정보 검사 테스트를 만든다.
3. 외부 PUBLIC 인바운드와 비동기 처리를 함께 가진 `bcm-webhook`에 먼저 적용한다.
4. `bcm-api`, `bcm-bat`, `bcm-admin`으로 확대하고 요청·거래·이벤트 상관관계를 관통 검증한다.
5. 중앙 수집 경계에서 schema 격리, 금지 필드 차단, 유실·지연 감시를 붙인다.
6. 보존 기간과 접근 역할을 승인하고 만료·삭제·법적 보류 훈련을 통과한다.
7. 기존 평문·중복 로그를 제거한 뒤 운영 정본을 구조화 JSON으로 전환한다.

## 완료 기준

- 네 BCM 프로세스가 같은 `bcm-log-v1` 계약과 공통 level 기준을 사용한다.
- 필수 운영·보안 사건과 서비스별 `eventCode` 소유자가 정해져 있다.
- Secret·서명·raw payload·PII가 애플리케이션 출력과 중앙 저장소에 없음을 자동 검사한다.
- 요청·거래·Webhook·이벤트·배치가 실제로 존재하는 식별자로 연결된다.
- 중앙 수집 장애가 업무 처리를 막지 않고 유실·지연·drop이 경보로 드러난다.
- 조회·다운로드·archive·정책 변경의 권한과 감사 경로가 검증된다.
- 분류별 보존 기간, 법적 보류, 만료 삭제와 모든 복사본 정리 책임자가 확정돼 있다.
- 일반 운영 로그, 감사 원장, 업무 DB 원문과 로컬 테스트 artifact의 정본이 섞이지 않는다.

## 미확정

- 중앙 수집·검색·archive 제품과 전송 방식
- `EPHEMERAL/OPERATIONAL/ERROR_SECURITY`의 실제 보존 기간과 backup 포함 삭제 SLA
- production에서 전체 블록체인 주소와 BCM `accountId`를 검색할 필요와 승인 권한
- stack trace 저장 범위와 제한 조회 역할
- 플랫폼 수집 영역·중앙 로그 저장소·보존 삭제의 조직별 책임자
