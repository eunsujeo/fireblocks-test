설계자 sweep 정책(2026-07 공유 · 일부 — 나머지 정책 자료 대기 중)을 우리 구조에 적용하는 설계다.
정책 자체는 그대로 옮기고, **"우리가 어떻게 처리하나"** — 트리거 계산·실행 방식·Fireblocks 기능 대응 — 를 정한다. 현행 흐름은 [블록체인 매니저 — 흐름](02-bcm-flow.md) sweep 절, 테이블은 [DB](03-bcm-db.md) `bcm_swp_trgt`.

## 정책 요약 — 두 계층의 sweep

| 계층 | 방향 | 트리거 | 실행 |
|---|---|---|---|
| ① 입금 모으기 | 받는주소 → 보내는주소 | 자산별 — 받는주소 잔액이 총자산 대비 일정 비율(예: 1%) 이상 · 가스비 한도 안에서 | 보유량 많은 순 M개 묶어 배치 전송, 완료 후 재체크 loop |
| ② 핫·콜드 균형 (밴드S) | 보내는주소 ↔ 콜드월렛 | 핫월렛백분율이 상한 초과 → 콜드로 · 하한 미만 → 콜드에서 충전 | 전 자산 동일 비율로 이동해 핫월렛균형으로 복귀 |

공통 전제:

- **Finalized 이후에만 sweep 대상** — 받은 tx 가 더블스펜딩이면 sweep tx 가 무효화돼 멤풀에 남고(가스 낭비·예측 못한 sweep), sweep 후 reorg 면 DB 에 rollback 레코드가 남아 복잡해진다.
- **받는주소 + 보내는주소(핫월렛)는 법정최대치 20% 를 넘을 수 없다** — 밴드 설계의 뿌리.
- 가치 기준은 **원화환산가치** = 이용가능잔액 × 고시환율 × NAV. NAV(순자산가치)는 토큰 1개를 실제로 뒷받침하는 준비금 가치 — 완전 준비금이면 ≈1, 준비금 가치가 움직이면 1에서 벗어난다. 액면 대신 실제 가치로 규제 비율(20%)을 재기 위한 보정이고, 환율과 함께 코어가 공급하는 회계 데이터다.

### 주소 3계층 ↔ 우리 구조

| 정책 용어 | 우리 구조 | 비고 |
|---|---|---|
| 받는주소들 | 고객별 vault (입금 식별·수신 전용) | 그대로 대응 |
| 보내는주소들 | 출금 풀 vault | 그대로 대응 |
| 콜드월렛들 | **현 설계에 없는 계층** | 후보는 아래 "콜드월렛을 무엇으로 두나" |

정책은 받는주소 → **보내는주소**로 모은다 — 현행 설계의 "고객 vault → 옴니버스" 와 목적지가 다르다. 옴니버스 계층을 유지할지(받는 → 옴니버스 → 출금 풀/콜드) 없앨지(받는 → 출금 풀 직행)는 나머지 정책 자료와 함께 확정한다(미확정).

### 밴드S 산식

| 항목 | 정의 |
|---|---|
| 총자산합 (=100%) | 받는주소+보내는주소+콜드월렛 전체 이용가능잔액의 원화환산 합 (가수금 포함) |
| 핫월렛합 · 핫월렛백분율 | 받는주소+보내는주소의 원화환산 합 · 핫월렛합×100/총자산합 |
| 핫월렛상한 | 법정최대치(20%) − 받는주소최대(예: 1%) − 버퍼(예: 1%) = 18% |
| 핫월렛하한 | 예: 5% |
| 핫월렛균형 | (상한−하한)/2 + 하한 — 예: 12.5% |
| 이동량 | 총Sweep합 = 핫월렛합 − 균형액 · **자산전송비율 = 총Sweep합/핫월렛합** — 전 자산 동일 비율, 이동 후 균형 도달 |

계산 예 (환율 1,000 · NAV 1): 콜드 41,010(74.5%) + 핫 14,005(25.5%) = 55,015 → 핫이 상한 18% 초과 → 균형 6,876(12.5%) → 총Sweep 7,129 → 비율 0.509 → 자산별 핫 보유량 × 0.509 를 콜드로.

## ① 입금 모으기 — 어떻게 처리하나

### 그대로 되는 것 — Finalized 조건

현행 설계가 이미 정책과 일치한다 — 입금 **확정(벤더 COMPLETED = DCCP 임계 도달, 계약 상태 `FINALIZED`)** 관찰 시에만 `bcm_swp_trgt` 에 마킹한다. 벤더 가이드도 같은 순서(COMPLETED 수신 → sweep 트리거)를 권장한다 ([Sweep to Omnibus](https://developers.fireblocks.com/reference/sweep-to-omnibus-1)).

### 바뀌는 것 — 트리거 기준

| | 현행 | 정책 적용 |
|---|---|---|
| 트리거 | 주기 배치 + **최소 금액**(운영 설정값) | 자산별 — 받는주소 잔액이 **총자산 대비 비율**(예: 1%) 이상 |
| 가스비 | 조건 없음 | **가스비 한도** — 비싼 타이밍 회피 (수수료 관측 주기 작업의 시계열을 판단 입력으로 씀) |

벤더 가이드의 권장 트리거 요인(잔액 임계·주기·네트워크 수수료 여건)과 같은 축이라 벤더 모델과 충돌이 없다. 비율 트리거의 분모(총자산합)는 원화환산이 필요해 아래 "환산 입력" 문제와 같이 걸린다.

### 실행 방식 — 배치를 어떻게 하나 (핵심 검토)

**전제 사실**: Fireblocks 의 sweep 은 **vault 당 개별 거래**다 — 여러 vault 를 한 온체인 거래로 묶는 배치가 벤더에 없다. 가이드 구현도 vault 를 돌며 거래를 하나씩 낸다 ([Sweep to Omnibus](https://developers.fireblocks.com/reference/sweep-to-omnibus-1)).

> 배치를 가능하게 하는 메커니즘(EIP-3009·2612·7702)의 원리·가스 구조·논스·감지 함정은 참고 문서 **[배치 sweep 메커니즘](98-batch-sweep.md)** 에 있다 — B 의 세부 방식(서명 기반 vs 상시 권한)은 그 문서를 읽고 벤더·발행사 확인 후 확정한다.

| 안 | 방식 | 온체인 tx 수 | 평가 |
|---|---|---|---|
| **A. per-vault 개별 (현행)** | 받는주소마다 거래 1건 — Universal Gasless 로 gas 는 relay 부담. M개 병렬 제출 | M | 벤더 네이티브 그대로. 배치 대비 gas 총량 큼 — 단 gas 는 relay 경유 인보이스 정산이라 "배치 컨트랙트 대비 비용 차이"가 실제 얼마인지 견적 필요 |
| **B. EIP-7702 배치 위임** | 받는주소(EOA)가 위임한 코드가 잔액을 움직일 수 있다 — 배치 sweeper 컨트랙트 1건의 거래가 M개 주소의 자산을 pull. authorization 여러 건을 한 거래에 싣는 것도 명세에 있다 ([7702 검토](../../블록체인매니저/가스대납/09-eip7702.md)) | 1 | 정책의 "배치 스마트계약"과 정확히 같은 그림. **단 Fireblocks 에서 위임 코드는 벤더가 정한다**(Vault account upgrade policy) — 벤더의 위임 지갑 구현이 제3자 배치 pull 을 지원하는지 미확인 · CSM/벤더 문의 대상 |
| C. 자체 배치 컨트랙트 (approve 기반) | 각 받는주소가 sweeper 에 approve → 이후 배치 transferFrom | 최초 M + 이후 1 | approve 자체가 주소당 거래 1건이라 첫 회 이득이 없고, 무제한 approve 는 위임 코드보다 넓은 상시 권한 — 수탁 리스크. 비추천 |

**채택**: **B — 배치 위임을 초기 설계로 한다** (2026-07 결정). 입금 건수가 많은 서비스라, 건당 고정비 상각(배치는 온체인 고정비를 한 번만 냄)·벤더 WRITE 호출량(per-vault 는 sweep M건 = 제출 API M번, WRITE 한도는 회신 대기 중)·부분 실패 운영(M건 건별 추적 대신 배치 1건)이 **처음부터** 문제가 되는 규모다.

단 B 는 우리가 만들 수 없는 **벤더 확인 2건이 성립 조건**이다 — 확인 전에는 A(벤더 네이티브라 확실)로 가고, 결렬 시엔 확장 미지원 자산만 A 로 남는다(아래 자산별 라우팅):

1. **위임 코드의 배치 pull 지원** — Universal Gasless 로 upgrade 된 vault(EOA)의 위임 지갑 코드가, 배치 sweeper 컨트랙트의 일괄 인출을 허용하는 구성이 가능한가.
2. **위임 pull 의 감지·기록** — 제3자 배치 거래로 vault 잔액이 움직일 때(본인 서명 거래 없이 — 7702 가 깨는 그 전제) Fireblocks 가 이를 **거래로 기록하고 웹훅을 내는가**. 안 내면 sweep 감지·대사가 설 자리가 없다 — B 의 성립을 가르는 질문.

B 채택으로 함께 확정되는 파장:

- sweep 거래가 **CONTRACT_CALL** 이 된다 → 미구독으로 둔 `transaction.network_records.processing_completed` 의 구독 검토 조건이 **발동**([감지 상세](99-detection-detail.md) 이벤트 표) — 감지·대사가 network records 를 펼쳐 M개 이동을 읽는 설계 필요.
- **배치 sweeper 컨트랙트**의 개발·감사 — 어떤 코드가 M개 주소의 자산을 움직이는지가 보안의 전부(7702 위임과 같은 원리).

### 세부 방식 — 자산별 라우팅 (단일 메커니즘 아님)

**전제: 다루는 자산 집합은 열려 있다** — 원화 SC 를 여럿 다루게 되고(KRWK 하나가 아님) 발행사가 제각각이라, 모든 자산이 3009/2612 확장을 지원한다고 가정할 수 없다. 따라서 sweep 메커니즘은 하나로 통일되지 않고 **자산의 능력에 따라 갈린다** — 자산 분리 운영이 폴백이 아니라 기본 구조다. (원리는 [배치 sweep 메커니즘](98-batch-sweep.md))

```
자산 온보딩 시 판정 — 이 토큰의 sweep 방식은?
① 토큰이 EIP-3009 지원?
├─ 예 → 3009 배치 — 안전 우선 (1회용·목적지 서명 고정 · 벤더 위임 코드 의존 없음)
└─ 아니오
   ② 벤더 위임 코드가 운영자 pull 을 지원? (문의 ③ — 자산 무관 공통 확인)
   ├─ 예 → 7702 배치 — 토큰 확장 불필요라 나머지 전부 커버
   └─ 아니오 → 그 자산만 A(개별) + 운영 보강
※ 공통 성립 조건 — 외부발 인출의 기록·웹훅(문의 ②)
※ 발행 스펙에 관여 가능한 자산(KRWK — 스펙 미정 = 지금이 요구 시점)은 EIP-3009 포함을 요구사항으로
```

- 자산 온보딩 절차에 **"sweep 방식 판정"이 항목으로 들어간다** — 확장 지원 여부를 확인해 3009/7702/A 중 하나를 그 자산에 배정.
- 벤더가 운영자 pull 을 열어주면 7702 가 "확장 없는 자산 전부"의 받침이 되고, 안 열어주면 그 자산들은 A 로 남는다 — 그래서 문의 ③이 커버리지의 폭을 정한다.

**A 로 남는 자산의 운영 보강**: 제출 pacing(sweep 은 급하지 않은 경로 — 벤더 호출 배분에서 출금 제출보다 낮은 순위로 큐잉) · 트리거 임계 조정(단 **받는주소최대 규제 안에서만** — sweep 을 미룰수록 받는주소 잔액이 쌓여 핫월렛 한도와 부딪힌다) · 가스비 창 활용. 병행으로 "위임 지갑 코드의 지정 운영자 인출"을 벤더 로드맵 요청으로 등록해 둔다.

### 논스

- B(채택): 제출 주체(배치 실행 계정)가 하나로 좁아져 그 계정의 논스가 직렬화 지점이 된다 — 여러 자산·연속 배치 loop 가 이 계정을 공유하므로 제출 직렬화(또는 논스 예약) 설계 필요(정책이 짚은 그 지점).
- A(폴백): 논스는 vault 별로 벤더가 관리 — 우리 몫 없음.

### M개 선정·loop

`bcm_swp_trgt` 에서 트리거 조건을 만족한 (계정, 자산) 중 **보유량 많은 순 M개** 선정 → 전송 → 완료 후 재체크 loop. 현행 "배치가 대상을 모아 제출"과 같은 뼈대라 테이블 변경은 트리거 컬럼 추가 수준이다(아래 파장).

## ② 밴드S — 어떻게 처리하나

### 환산 입력 — 누가 계산하나 (결정 필요)

밴드 판정에는 **고시환율·NAV** 가 필요하다. 이는 매니저가 모르는 회계 데이터다 — 매니저는 체인 단위 잔액만 안다. 후보:

1. **(추천) 판정은 코어·실행은 매니저** — 코어(정산/Admin 평면)가 환산·밴드 판정을 하고, 매니저에 "자산별 이동량" 지시를 내린다. 매니저는 온체인 이동의 단일 창구라는 현 경계 유지.
2. 매니저가 판정까지 — 환율·NAV 를 매니저에 공급해야 해서 경계가 흐려진다. 비추천.

### 핫 → 콜드 (상한 초과)

- 출금 풀 → 콜드월렛 전송. 출금 풀에서 나가는 거래이므로 **TAP 정책 + Co-signer 서명 경로를 그대로 지난다** — 목적지(콜드 주소)를 TAP 화이트리스트에 넣는 것이 통제의 핵심.
- 전 자산 동일 비율(자산전송비율) 적용 — 지시 단위는 (자산, 이동량) 목록.

### 콜드 → 핫 (하한 미만 · 충전)

- 콜드월렛의 서명이 필요하다 — **콜드는 정의상 오프라인 서명이라 자동화에 한계**가 있다. 하한 경보 → 사람이 승인·서명하는 운영 절차로 두는 것이 현실적(자동 충전은 콜드의 의미를 깎는다).

### 콜드월렛을 무엇으로 두나 (확인 필요)

| 후보 | 내용 | 상태 |
|---|---|---|
| Fireblocks **cold workspace** | 벤더가 hot/cold workspace 를 제공 — cold 는 오프라인 서명 ([workspace 구조](https://developers.fireblocks.com/docs/create-direct-custody-wallets)) | 벤더 네이티브 후보. 워크스페이스 간 이동 경로·수수료·우리 API user 권한 구조는 확인 필요 |
| 외부 콜드 (자체·타사) | 일반 출금과 같은 외부 전송 | TAP 화이트리스트로 통제. 콜드→핫 충전 절차는 그쪽 서명 체계 따름 |

## 미확정 · 벤더 문의 후보

- **★ B 성립 조건 2건 — 최우선 문의.** ① "Universal Gasless 로 upgrade 된 vault 들에 대해, 위임 코드가 제3자 배치 컨트랙트의 일괄 인출을 허용하는 구성이 가능한가." ② "그 배치 거래로 vault 잔액이 움직일 때 Fireblocks 는 vault 별 거래 기록·웹훅을 어떻게 내는가 (networkRecords 로 오는가)." — ①이 결렬되면 3009 미지원 자산은 A 로, ②가 결렬되면 배치 전체가 A 로.
- **옴니버스 계층 유지 여부** — 정책은 받는→보내는 직행. 나머지 정책 자료와 함께 확정.
- **cold workspace 간 이동 경로** — 같은 Customer Domain 내 워크스페이스 간 전송 방식·수수료·정책 통제.
- **비율 트리거의 분모 산출 주기** — 총자산합(원화환산)을 얼마나 자주, 누가 갱신하나 (밴드S 환산 입력과 같은 결정).
- **M·버퍼·상하한·받는주소최대 값** — 운영 설정값. 정책 예시(1%·18%·5%·12.5%)는 예시.
- **가스비 한도의 기준** — 수수료 관측 시계열의 어떤 지표(절대값·백분위)로 끊나.
