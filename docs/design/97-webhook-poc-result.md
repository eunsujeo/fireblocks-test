[감지 상세](99-detection-detail.md)의 수신 경로를 실물로 검증했다. 실제 Fireblocks 웹훅으로 네 시나리오를 돌린 결과다(2026-08-03).

## 환경

- Fireblocks **웹훅 v2** · US 프로덕션 스택(api.fireblocks.io) · testnet 입금 이벤트
- 구독은 설계와 동일하게 `transaction.created` · `transaction.status.updated` · `transaction.approval_status.updated` 3종
- 서명 검증: 벤더가 알림 본문에 서명을 붙여 보내고, **벤더 공개키로 그 서명을 검증**한다. 공개키는 벤더가 게시하는 주소(JWKS)에서 가져와 캐시하고, 키가 교체되면 다시 가져온다

수신기 구현·배포 환경은 fbhook 저장소에 있다.

## 시나리오 한눈에

| # | 시나리오 | 결과 |
|---|---|---|
| 1 | 실입금 수신 | 감지·확정 알림 2건 수신 · 서명 검증 통과 · payload 필드 전부 확인 |

| 4 | `resend_failed` 호출 | `202 {"total":1}` → 51초 뒤 재수신 |

## 1. 실입금 수신

**한 것** — testnet 에서 외부 지갑 → vault 로 KBKRW 테스트 토큰 100 전송.

**결과** — `transaction.created`(`CONFIRMING`·컨펌 1) → `transaction.status.updated`(`COMPLETED`·컨펌 3), 같은 tx 로 두 건이 왔다. 서명 검증 통과 후 적재·처리까지 정상.

payload 필드가 설계 가정과 일치했다:

- 최상위 `id`(알림 UUID) · `eventType` · `resourceId`(= tx id) · `webhookId` · `workspaceId` · `createdAt`(epoch ms)
- `data.{id, status, subStatus, numOfConfirmations, source, destination, txHash, blockInfo, amountInfo}`
- `transaction.created` 가 이미 `CONFIRMING` + `txHash` + `blockInfo` 를 담고 온다 — 입금 알림은 체인에 올라간 뒤부터 시작한다
- 금액은 `data.amountInfo` 가 **문자열**이다 — 정밀도 손실을 피하려면 이 값을 쓴다

원문은 [웹훅 payload 실물 샘플](96-payload-sample.md).

## 2. 서명 없는 알림·가짜 서명 알림 전송

**한 것** — 서명 헤더가 없는 알림, 그리고 벤더 서명이 아닌 **가짜 서명**을 붙인 알림을 각각 보냈다.

**결과** — 둘 다 **401** 로 거절했다. 수신 주소는 공개돼 있어 누구나 보낼 수 있지만, 서명이 맞지 않으면 받지 않는다.

참고 — **본문이 한 바이트라도 다르면 거절된다**는 것도 확인됐다. 저장했다 꺼낸 본문에 원래 서명을 붙여 보냈더니 401 이었다(꺼낸 값은 내용은 같아도 바이트가 달랐다). 다만 이를 위한 시나리오를 따로 돌린 것은 아니다.

## 3. 적재 실패 후 복귀 — 재시도 간격

**한 것** — 적재를 500 으로 실패시켜 두고 벤더 재시도가 도착하는 시각을 기록. 이후 정상으로 되돌림. (알림 2건에 대해 2회)

**결과** — 복귀 후 다음 재시도에 전량 들어왔다. **유실 없음.** 재시도 간격은 이렇게 벌어졌다:

```
1차 실패 후: +21~60초 → +1분 → +1분* → +3분 → +6분 …   (* 회차에 따라 1분 라운드 1~2회)
```

도착 시각이 **분 tick(:00)에 정렬**된다 — 벤더가 분 단위로 재전송을 배차하는 것으로 보인다. 공식 문서는 "지수 백오프 총 10회·합산 약 8시간"이라 밝히고 있고 초 단위 간격(10·30·120·300·900초…)이 자주 인용되는데, **측정값은 그와 다르다.**

## 4. resend_failed 호출

전제 — 벤더는 알림마다 성공·실패 상태를 들고 있다. 200 을 주면 전달 성공으로 두고 더 보내지 않고, 200 을 못 주면 실패로 두고 스스로 재시도한다. `POST /v1/webhooks/{webhookId}/notifications/resend_failed` 는 **호출한 순간 실패 상태인 알림들을 다시 보낼 목록에 올린다.**

**한 것** — 시나리오 3 의 상태(실패 2건)에서 호출.

```
① 500 으로 알림 2건이 실패 상태
② 벤더가 스스로 재시도하는 중
③ 서버를 정상으로 되돌림
④ 그 사이 재시도 1건이 들어와 200 을 받음  → 그 1건은 전달 성공으로 바뀜
⑤ resend_failed 호출                      → 202 {"total":1}
⑥ 51초 뒤                                  → 그 1건이 도착
```

**결과** — 세 가지가 나왔다:

- **`total` 은 호출 시점에 실패 상태인 알림 수다.** 실패했던 2건 중 1건이 ④에서 전달 성공으로 바뀌어 `total:2` 가 아니라 **`total:1`** 이었다 — 이미 2xx 를 받은 알림은 목록에 오르지 않는다.
- **`202` 는 접수증이고 알림 도착은 따로다.** 응답은 곧바로 왔지만 알림은 ⑥에서 왔다(51초 뒤) — 벤더가 분 단위로 배차한다.
- 그래도 기다리는 것보다 빨랐다 — 그냥 뒀으면 4분을 더 기다려야 했다.

## 추가 실측 — tx 대사 예행

**조회·대조 경로만 일회성 스크립트로 예행**했다 — 벤더 `GET /v1/transactions` 와 인박스를 대조.

**결과** — 대조가 의도대로 돌았다. 쿼리 패턴도 QnA 확답대로였다: `after` 를 `createdAt` 기준으로 명시하고 `orderBy` 를 지정하지 않으면 next-page 커서가 정상으로 온다. 대조한 6건에 **상태 불일치 0건**.
